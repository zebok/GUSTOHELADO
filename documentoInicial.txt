1. El proyecto
Qué es: una app de una sola pantalla que, dado un punto geográfico (GPS, dirección o coordenadas), recomienda a qué heladería de CABA ir a tomar un helado, según el antojo del usuario y cuánto está dispuesto a caminar.

El impulso: como catador serial de helados en CABA, el problema recurrente es: estando en un punto cualquiera, ¿cómo decidir a dónde ir minimizando el esfuerzo de traslado y maximizando la satisfacción según mi experiencia histórica?

La hipótesis: dado un punto geográfico X y un perfil de antojo, existe una combinación óptima entre la satisfacción histórica (score) y la fricción del traslado (distancia) que maximiza el éxito de la experiencia.


2. Decisiones de arquitectura (y su porqué)
Jamstack / JSON estático como "base de datos". La data se sirve como un JSON precalculado y estático. Es chico (kilobytes), vuela en performance, cuesta $0 de infra y no hay servidor que mantener.

División del cómputo:

Todo lo que NO depende del usuario lo precalcula el pipeline de Python (joins, agregaciones, score histórico por heladería y por categoría).
Lo que depende de la ubicación en vivo lo calcula el front (distancia con Haversine desde el GPS + ranking final). Esto no se puede precalcular porque depende del punto del usuario en runtime.

React + Vite + TypeScript, no Astro. La app es interactiva de punta a punta (GPS, sliders, filtros que mueven el mapa, Top que se recalcula, gráficos reactivos). Astro brilla en sitios mayormente estáticos con islitas de interactividad; este caso es lo opuesto. React es además el skill de front más demandado en el rubro objetivo (fintech/producto).

TypeScript desde el inicio: se define la forma de la data una sola vez y el compilador previene errores de tipos en todos los componentes.

5.3 Tipos TypeScript (src/types.ts)
export type MacroCategoria =

  | "CHOCOLATE" | "DULCE DE LECHE" | "CREMA" | "FRUTA" | "AUTOR" | "MISC";

// Los 5 botones del filtro (MISC existe en data pero no es botón)

export type Antojo = Exclude<MacroCategoria, "MISC">;

export interface Heladeria {

  id: number;

  idCadena: number | null;

  nombre: string;

  direccion: string;

  lat: number;

  lng: number;

  activa: boolean;

  visitas: number;

  scorePorCategoria: Partial<Record<MacroCategoria, number>>; // precalculado en Python

}

export interface BaseDeDatos {

  generadoEl: string;

  heladerias: Heladeria[];

}

export interface Ubicacion {

  lat: number;

  lng: number;

  origen: "gps" | "texto" | "coords";

}

// Lo que el front arma en runtime (suma la distancia viva)

export interface ResultadoRankeado {

  heladeria: Heladeria;

  distanciaMetros: number;

  scoreFinal: number;

}

6.2 Flujo de estado (regla: lift state up)
App posee: la BaseDeDatos cargada (una sola vez, vía lib/data.ts) y la tab activa. Pasa la data como prop a las dos vistas (props alcanza para esta profundidad; no usar Context todavía).
RecommenderView posee el estado del recomendador: userLocation: Ubicacion | null, maxDistanceMeters: number, selectedAntojo: Antojo. Deriva los resultados con useMemo a partir de (data + userLocation + selectedAntojo + maxDistanceMeters).
Los controles son componentes controlados "tontos": LocationInput, CravingFilter y DistanceSlider reciben value + onChange y reportan hacia arriba. No guardan estado propio.
MapView y ResultsList son consumidores puros: reciben results: ResultadoRankeado[] y userLocation ya calculados. No computan nada.
6.3 Lógica fuera de los componentes
lib/geo.ts → haversineMetros(a, b): number.
lib/scoring.ts → rankear(heladerias, ubicacion, antojo, maxDistanceMeters): ResultadoRankeado[] (sección 7).
lib/data.ts → fetch del JSON desde /data/heladerias.json y tipado a BaseDeDatos.
6.4 Las dos pestañas
Tab 1 — 🔎 El Recomendador: input de ubicación, slider de distancia, botones de antojo, mapa con el Top y las cards de resultado.
Tab 2 — 📊 El Perfil del Catador: gráficos con insights personales (clásicos vs. autor, ranking por barrio, etc.). Lee el mismo JSON.


7. Lógica de scoring y distancia — default v1
Implementar este default. Está marcado como decisión a iterar (sección 11).

Distancia: Haversine entre userLocation y cada heladería, en metros.
Filtro duro por radio: descartar heladerías con activa === false y las que estén más lejos que maxDistanceMeters (el slider actúa como radio máximo en v1).
Filtro por antojo: considerar solo heladerías que tengan scorePorCategoria[selectedAntojo] definido.
Score final (blend normalizado, pesos por default 0.7 / 0.3, tuneables):
normScore = scorePorCategoria[antojo] / 10
normProximidad = 1 - (distanciaMetros / maxDistanceMeters)  // dentro del radio: 0..1
scoreFinal = 0.7 * normScore + 0.3 * normProximidad
Resultado: ordenar por scoreFinal descendente y devolver el Top 3.

10. Definición de "hecho" (qué debe quedar funcionando)
Repo scaffolded con la estructura de la sección 4.
npm install && npm run dev levanta la app sin errores.
La app carga public/data/heladerias.json (seed) y renderiza el mapa con los marcadores.
El usuario puede fijar ubicación por GPS y por input de texto/coordenadas.
El slider de distancia y los botones de antojo filtran y recalculan el Top 3 en vivo.
El mapa muestra la ubicación del usuario + el Top 3; las cards muestran nombre, distancia y score.
La Tab 2 renderiza al menos un gráfico con Chart.js a partir del seed.
La app es instalable como PWA.
README.md con descripción, stack, cómo correr en local y cómo se regenera la data.

11. Decisiones pendientes (para iterar)
Slider de distancia: filtro duro vs. peso blando. v1 lo trata como radio máximo (filtro duro). Alternativa futura: que el slider modifique el peso de la distancia en el score (slider corto → la cercanía pesa más; slider largo → casi solo importa el score histórico).
Fórmula y pesos del scoring. Los pesos 0.7 / 0.3 son un default; ajustar con datos reales.
Distancia real de caminata. v1 usa Haversine (línea recta). Mejora futura: pedir distancia de caminata real a una API de ruteo gratuita (OSRM / OpenRouteService) solo para los finalistas.
Geocodificación de nuevas heladerías. Evaluar Nominatim (OSM) para mantener todo en el ecosistema gratuito/abierto, consistente con los tiles de OSM.
Migración a TypeScript estricto / CI/CD. Más adelante: un GitHub Action con cron que regenere el JSON desde la Sheet automáticamente.
